## 2. 原有设计及容易混淆的概念

### 2.1 两个线程、两个队列

`DataAcquisitionService` 与流程/UI 位于主线程；`AcsClient` 在 ACS 工作线程同步调用 SDK。请求使用 queued invocation 发给 ACS，结果信号排队返回主线程。

“ACS 已经读完并发送回调”不表示“主线程已经执行回调”。消费序号只有在主线程 `onBlockRead()` 校验通过后才推进。单次 `QTimer::stop()` 只取消尚未发生的定时触发，不能撤销已经入队的请求或结果。

### 2.2 状态和序号

| 字段 | 含义 |
|---|---|
| `DCSTART_CON` | 采集开关；SDK 写入成功只证明开关已写入 |
| `DC_ACTIVE_BLOCK` | 控制器正在写的物理块；0 表示没有活动块 |
| `DC_BLOCK_SEQUENCE` / `publishedSequence` | 本次控制器采集会话累计发布到的逻辑序号 |
| `DC_BLOCK_SEQ_MAP` | 五个循环物理块各自对应的逻辑序号 |
| `lastConsumedSequence_` | 上位机已经接收并消费的逻辑序号 |

每次控制器采集会话开始，常驻采集 Buffer 都清零序号与块元数据，然后从 1 重新发布。块 1 与序号 1 是不同概念：块号循环复用，逻辑序号在同一会话内递增。

`published=0` 只表示还没有发布完成块；控制器可以已经开始向活动块写样本。停止时会发布不足整块的尾块，所以一个原本较长的 `published=0` 窗口会因快速停止而变得很短。

## 3. 故障 A：同一尾块被读两次

### 3.1 日志时间线

| 时间 | 事件 |
|---|---|
| 13:50:44.918 | 主线程请求 `block=1, expected=1`，`lastConsumed=0` |
| 13:50:44.994 | ACS 完成读取并发送块回调 |
| 13:50:46.932 | 主线程先处理另一份元数据，仍看到 `lastConsumed=0`，再次请求块 1 |
| 同一时刻，随后 | 第一份块回调才被主线程消费，`lastConsumed=1` |
| 13:50:49.001 | 第二份块 1 回调到达，此时期望 2，触发错误 |

两次回调都是同一序号、同样的 4181 点尾块。本段证据没有显示控制器漏发序号 2。

### 3.2 为什么多数时候不触发

停止路径原先同时启动 50 ms 单次查询定时器，并写入关闭开关。关闭回执还会立即发起查询。

若关闭回执及时到达，回执处理会取消尚未触发的定时器，只留下单条查询链。即使出现两份查询结果，只要第一块先消费完，后续选择也会看到更新后的消费序号。

失败要求出现特定交错：另一份元数据已经排队，且在第一份块回调被消费前得到处理。缺少在途标记时，两次选块都认为自己应读 1。此次主线程块回调等待约 1.94 秒，明显扩大了竞争窗口；ACS 第一块读取约 75 ms。日志不能区分 UI 同步工作、嵌套事件循环、事件积压或调试暂停各自的贡献。

只忽略重复序号会掩盖请求重叠，且不解决跨会话的旧回调。本次在请求调度处防重，并保留严格连续性检查。

## 4. 故障 B：新会话继承了旧基线

### 4.1 原来的正常路径为什么能成功

以上一轮结束于序号 2 为例：

1. `startCollection()` 把本地消费序号置 0，进入 Starting。
2. 启动前先查空闲，控制器仍保留旧元数据：`control=0, active=0, published=2`。
3. 原代码把 `lastConsumed` 又设为旧 `published=2`，意图跳过旧块。
4. 上位机写 `DCSTART_CON=1`；控制器开始新会话，清零序号和块元数据。
5. 如果主线程及时处理开启回执并查询到 `published=0`，原代码执行“发现 0 则把本地消费序号清零”。
6. 新会话随后发布 1，上位机从 1 接收，表面正常。

这实际混用了两套协议假设：上位机采用“跨会话累计序号、启动继承基线”，控制器采用“每会话从零重置”。查询恰巧观察到 0，暂时掩盖了不一致。

| 13:57:33.166 | 首轮尾块 2 消费完成，`lastConsumed=2` |
| 13:57:33.186 | 首轮排空结束，进入 Idle |
| 13:57:34.812 | 第二条记录请求启动采集，进入 Starting |

| 13:57:35.609 | 主线程处理开启回执时已在 Stopping，旧代码不执行启动确认查询；随后关闭回执触发尾块查询 |

这里 619 ms 是 `34.940 → 35.559`：**启动前的空闲检查结果等待主线程处理**，不是尾块传输，也不是开启后的确认查询。具体阻塞原因没有被日志证明。

控制器经历的是 `旧会话2 → 新会话0 → 新会话1`；上位机只观察到了 `旧会话2 → 新会话1`。该错误发生在元数据检查阶段，还没有请求新会话块 1。

### 4.3 为什么有时不触发，甚至没有报错也可能不正确

- 正常运动持续较久，首块尚未发布，轮询容易看到 0，于是旧基线被纠正。
- 启动确认回调及时处理，也更容易在运动结束前观察到 0。
- 运动快结束才启动采集，停止会迅速发布小尾块，可能完全错过 0。
- 若旧基线恰好也是 1，新会话也发布 1，原逻辑可能把新块误认为已经消费并直接排空，表现为无报错但少数据。
- 首轮额外定位数据可能把旧基线从 1 推到 2，使新会话 1 明确小于旧基线，从而显性报错。不能把“不报错”当作会话协议正确的证据。

## 5. 排空约 120 ms，为什么反向已经开始

以下时间都在 13:57:33：

| 时间段 | 内容 | 墙钟差值 |
|---|---|---:|
| .065 → .081 | 收到状态 55、请求关闭、读取尾块元数据 | 约 16 ms |
| .081 → .166 | 读取 5838 点 × 6 通道，校验并转换 | 约 85 ms |
| .166 → .169 | 主线程消费并发布尾块 | 约 3 ms |
| .169 → .185 | 再查元数据，确认没有活动块和未读块 | 约 16 ms |
| .186 | 切换 Idle | 从停止请求约 121 ms |

内部排空计时器记录 119 ms，与时间戳差值基本一致。矩阵传输时间戳 `.084 → .163` 约 79 ms，是主要耗时。尾块回调 `.166` 发出并在同一毫秒被主线程处理，本段不存在约两秒的块回调等待。

`.170` 是上位机收到状态 70 的时刻，不是控制器运动开始的精确时间。相对 `.186` 仅提前 16 ms。控制器状态 55 后执行 `WAIT L_RESULT_WAIT`，然后无条件推进状态 70；没有检查上位机排空完成或下一条采集准备完成。源码注释“等待上位机完成”不等于存在确认握手。

排空完成也不等于下一条采集就绪：还要经过当前记录数据库收尾、下一条建表和启动确认。日志中这些步骤直到 `34.812` 才发起下一条采集。因此不能仅把矩阵传输优化几十毫秒视为完整修复。

仓库中 `G_RESULT_WAIT` 的默认值/注释不能证明现场加载值或实际时长；状态回调间隔也不能直接证明控制器 WAIT 单位。本次未改变等待参数。

## 6. 用户观察：不在零点容易出问题，从零点出发通常正常

首次流程是：建表 → 开启采集 → 发布 collectionStarted → 启动整段运动。控制器执行状态 30 返回零点、状态 40 定位到起点、状态 50 正向测试。采集 Buffer 只等 `AST(X).#MOVE`，没有判别运动属于哪个阶段。

一旦任意运动触发采集，采样循环只受 `DCSTART_CON` 控制，中间静止不会自动结束本次采样。因此初始不在零点，返回零点会提前触发第一条采集，并可能包含随后去皮等待、起点定位及正式正向测试。

附件证据：

| 时间 | 事实 |
|---|---|
| 13:57:10.544 | 进入 Collecting |
| 13:57:10.580 | 上位机收到状态 30 |
| 13:57:27.515 | 已消费第一整块 16666 点 |
| 13:57:29.313 | 上位机收到状态 40 |
| 13:57:30.878 | 才收到正式正向测试状态 50 |
| 13:57:33.166 | 尾块 5838 点；首条原始数据总计 22504 点 |

从零点开始会省去返回零点的实际位移，使第一次触发采样更晚、数据量和会话时序不同。但零点与测试起点不相同时，状态 40 仍可能提前触发采样。该观察支持采样边界有问题，不证明位置本身直接导致重复读块。

`handleAcquisitionBlock()` 先把整个块交给数据库，图表才按位置范围筛选。单纯位置筛选不能识别“准备定位经过此处”和“正式测试经过此处”；因此也不能据此保证原始数据或区间统计纯净。

额外数据确实形成了旧序号 2；它是否直接造成 619 ms 主线程延迟，证据不足。需要单独测量槽函数耗时、事件排队时间和 UI 更新，而不能根据关联推定原因。

## 7. 本次解决方案与实现

### 7.1 控制器会话请求/回执

在 `motorbuffer/all.prg` 新增两个 GLOBAL INT：

- `DC_SESSION_REQUEST`：上位机在开启采集前写入正会话号。
- `DC_SESSION_ACK`：控制器完成本次初始化后发布的会话回执；初始化期间为 0。

上位机先确认控制器稳定空闲，根据旧 ACK 选择下一个会话号（INT 最大值后回到 1），先写 REQUEST，再写 `DCSTART_CON=1`。控制器进入新会话后先置 ACK=0，清理全部旧元数据，最后置 ACK=REQUEST。ACK 在会话停止后保留，直到下一次初始化。

读取元数据时，在状态和数组读取前后分别读取 ACK。只有两次 ACK 都匹配本次请求，才接受为新会话。匹配回执证明旧元数据已经清除，无需观察 `published=0`。即使首份有效元数据已经 `published=1` 或更大，本地仍从 0 开始按连续序号读取。

初始化确认设置 5 秒超时，在元数据回调处检查；这不是能中断阻塞 SDK 调用的独立看门狗。确认后 ACK 意外改变、真实序号回退仍报错。块传输前后也核对 ACK，防止读取期间控制器会话切换后发布混入的数据。

### 7.2 在途保护与主机 generation

- 元数据/块请求从入队到主线程处理回调期间保持在途；存在读取或控制写入未完成时，新的查询触发被合并。
- 块回调推进序号并执行 `blockReady` 后才释放块标记，避免同步槽中的事件重入提前发起下一条读取。
- 关闭回执、块成功、块拒收都沿同一回调链继续查询；无新块时才使用单次定时器退避。
- 停止入口取消原有“同时启动定时器并等待关闭回执”的双触发策略。
- 所有采集控制、元数据、块成功/拒收和失败结果都携带主机 `generation`。开始、完成、故障、复位恢复和关闭时失效旧代；旧结果不会清除新代在途标记或改变新代序号。
- 控制器会话号与主机 generation 用途不同：前者证明设备元数据属于本次初始化，后者识别线程队列中的旧任务结果，不能互相替代。

已经进入 ACS 队列的命令并非物理撤销；回调隔离不代表 SDK 命令未执行。关闭与队列顺序、已有机器命令 epoch 校验仍共同承担收尾职责。

### 7.3 Starting 期间收到正常停止

| 停止时进度 | 行为 |
|---|---|
| 尚未提交开启命令，仅在做启动前检查 | 完成本次取消，失效旧检查回调，不消费上一会话数据 |
| 已提交开启，尚未收到匹配初始化回执 | 保持 Stopping，继续确认会话；收到匹配 ACK 后写关闭，再读取本次尾块 |
| 已确认新会话 | 正常写关闭并排空 |
| 初始化迟迟没有匹配 ACK | 超时进入 Fault，并请求关闭采集 |

这样避免过短的 1→0 脉冲导致控制器尚未初始化就被取消，从而把旧元数据误认为新尾块。等待的是采集初始化，代码不会因此阻止流程层发送运动停止或设备的独立安全停止。

### 7.4 故障收尾和保留的检查

Fault 中再次调用 `stopCollection()` 不会再进入 Stopping；故障路径统一提交关闭命令。保留块序号严格连续、真实发布序号回退、环形覆盖、读块前后稳定性检查。没有通过“忽略重复序号”消除报错。

| 控制开关已写入，开启回执尚未处理，收到正常停止 | 等匹配 ACK 后关采集，正确排空短尾块 |
| 启动前空闲检查还在队列中就停止 | 旧回调作废，不再开启采集 |
| 人为延迟主线程处理块回调 2 秒，多次触发查询 | 同一块不重复入队，只发布一次 |
| blockReady 同步槽重入请求元数据或停止 | 在途保护保持，返回后继续单链查询 |
| 故障/复位/重新开始后注入旧代成功、拒收、错误回调 | 不影响当前会话、在途标记或消费进度 |
| 同一会话缺少下一序号、只看得到更后面的块 | 继续报告覆盖或不连续 |
| 读块期间 ACK 改变 | 不发布该块，报告会话改变 |
| 控制器未更新协议或初始化回执不推进 | 启动明确失败/超时，不读取旧数据 |
| 初始位置在零点/不在零点、多轮正反向 | 分别核查序号、点数和准备位移；不以无报错代替采样边界正确 |

## 9. 独立问题的后续方案

### 9.1 正式运动采样边界

准备定位阶段与正式测试阶段应有明确界限。可在控制器侧增加“正式段允许采样”的条件，使会话准备就绪与实际开始采样分开；在正式运动前完成采集准备，准备定位不产生测试样本。若仅在主线程轮询看到状态 50/70 后才开启采集，会因通信/队列延迟漏掉正式段开头，不应作为可靠边界方案。

具体边界是整个正式运动段还是配置的位移区间，需要按实验需求确定。此次仅记录方案，没有修改运动或样本筛选规则。

### 9.2 下一段就绪握手

控制器下一段运动应由“上一条收尾完成且下一条采集准备就绪”的明确条件放行，配合超时和停止退出；不能靠不断增大固定 WAIT 来保证正确。仅有本次新增的采集初始化 ACK，还没有让运动程序等待下一条记录准备完成，所以它不解决反向运动先启动、采集后开启导致的缺样。

### 9.3 主线程延迟定位

建议给每个请求记录 generation、控制器 session、请求入队、ACS 开始/结束、主线程回调开始/结束时间，分别计算 ACS 排队、通信传输和主线程排队耗时。对数据库收尾回执、统计回执、图表刷新与模态进度窗口的同步槽增加耗时测量。当前日志仅证明存在排队延迟，不能直接认定是某个 UI 控件或数据库操作造成。
