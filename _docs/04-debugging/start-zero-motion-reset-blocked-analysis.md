# 测试前移零被拒绝、故障收尾顺序及复位被阻塞

本记录只整理用户描述、日志证据、代码推论及后续设计建议，不代表已实施或验证修复。本轮不修改业务代码、不运行程序或离线检查。

## 1. 用户描述与期望

用户报告三个关联现象：

1. 有时无法进行第一段运动，当时看不出具体原因，希望除诊断外增加日志。
2. 出错后不能复位，提示“实验收尾或运动尚未结束”。重点是故障处理和复位的优先级：应先完成错误处理，再进入最终故障状态、弹出故障提示；故障必须有可用的复位路径。
3. 怀疑 `MotionControlService::hasActiveMotion()` 导致 `moveToZero()` 无法正常完成；重启软件也无效。状态位较多，需要明确哪些表示硬件事实、哪些表示命令等待、哪些表示业务阶段。

其中“重启仍无效”和复位被拒绝来自用户描述，本次附件没有记录重启后的第二次运行，也没有复位点击日志。

## 4. 历史路径为何可能形成无法复位的闭环

### 4.1 一个总布尔值合并了不同状态

历史 `hasActiveMotion()` 的判断为：

```cpp
zeroMovePending_ || currentStatus_.axisMoving
    || std::abs(currentStatus_.feedbackVelocityMillimetersPerSecond) > 0.001
    || (!protectionStopped_ && (maintenanceCommandPending_
        || currentStatus_.homeRunning || isActiveState(currentStatus_.state)))
```

它混合了移零命令在途、轴运动反馈、速度阈值、维修命令在途、回零状态和控制器程序状态。返回 `true` 不能解释到底是哪项阻塞，也不等于控制器程序正在执行实验。

历史 `moveToZero()` 将连接、首帧状态、模式、回零完成、程序状态及 `hasActiveMotion()` 等条件合并成一句“当前状态不允许……”。因此本日志无法单凭拒绝消息定位具体条件。

### 4.2 启动、停止、复位使用了不一致的判定

历史停止逻辑优先处理 `zeroMovePending_`，否则要求 `isActiveState(G_STATE)`，状态 0 会返回“没有可停止的运动”。而流程故障时，只有 `hasActiveMotion()` 为真才调用停止。

```text
启动：宽泛的运动判定为真 → 不允许移零
故障清理：同一宽泛判定为真 → 尝试停止
停止：程序状态为 0 → 拒绝停止
复位：宽泛判定仍为真 → 拒绝复位
```

这是一条代码上可达的恢复死路：认为“存在需要停止的活动”的入口，与“允许执行停止”的入口没有一致的语义。

结合历史代码，移零入口拒绝时尚未设置本次 `zeroMovePending_`；机器故障监听还会清理维修命令和本地回零标志。停止时程序状态又为 0，因此 `axisMoving` 或速度绝对值超过 `0.001 mm/s` 是值得优先核查的来源。但日志未打印这些值，也不能完全确认二进制版本，此结论属于较强推论，不是已证实的根因。真实运动、反馈噪声、陈旧快照、单位转换均不能在现有证据下定论。

### 4.3 复位拒绝消息掩盖了实际阻塞项

流程复位入口将以下条件合并：

```cpp
hasActiveExecution() || pendingTerminalState_.has_value()
    || MotionControlService::instance().hasActiveMotion()
```

任一成立都提示“实验收尾或运动尚未结束，不能复位”。这无法区分执行上下文、异步收尾和运动反馈。

本次日志已出现整组完成通知，不能直接断言“实验收尾永远没完成”。若用户在后续流程上下文清理后点击复位，运动判定仍为真的可能性更值得排查；但没有复位时刻的状态日志，尚不能排除其他分支。

重启只会重建应用内存状态，重新连接后仍可能读到相同的控制器/模拟器反馈。这与用户“重启无效”相容，但不是持久状态异常的证明。

## 5. 故障顺序与状态管理的其他问题

历史故障路径先进入机器故障、发出 `executionFailed`，然后才尝试停止和收尾。若同步信号触发模态弹窗，调用链尚未执行后面的清理，界面就先要求用户处理故障。`a4f811b` 将失败通知改为排队执行，可减少直接打断调用链，但“通知排队”仍不等于“运动、采集、数据库均已清理完毕”。

`finishPendingTerminalState()` 是流程终态收束：发布待定的最终结果并清理执行上下文。它本身不是硬件停止确认；不能因为这个函数执行了，就推断轴已静止、控制器已复位。

另外有以下代码风险，尚非本日志直接证实的故障：

- 历史 ACS 移零使用同步 `acsc_WaitMotionEnd(..., 10000)`，与轮询、排队停止共用工作线程，等待期间可能延迟后续命令。此次移零入口已拒绝，不能用它解释本次失败。
- 服务层与客户端各有移零等待状态，需保证提交失败、异步失败、断连、超时、取消都结束同一命令生命周期，避免残留标志。
- 上层故障处理改写 `homeRunning` 等字段，会把硬件反馈和本地命令状态混在一起。清理软件标志不等于收到硬件停止反馈。
- 实验表处于 Creating/Finishing 时，如果缺少超时和回调失败出口，流程可能无限等待。DBG-008 的防重复提交不等于已解决所有等待问题。
- 复位命令提交/SDK 调用返回，不能自动代表复位完成。还需新的状态反馈以及采集、数据库状态恢复结果；仅发出 `controllerResetCompleted` 不足以证明整个系统可再次开始。

## 6. 整理时当前工作区的差异

当前运动文件已有另外的改动，本次保持原样：移零改为运行 Buffer 8；轮询增加 `bufferRunning`；服务层在首帧或 Buffer 状态变化时发送零位到达信号；`hasActiveMotion()` 暂时直接返回 `false`。这些变化不能反向解释旧日志，也没有本次运行证据支持其效果。

从设计上看，直接返回 `false` 会绕过原有检查，却没有证明运动已结束；Buffer 状态发生变化也不天然代表当前移零成功，首帧、启动沿、停止沿、失败退出应区分，并关联当前命令及目标位置。工作区还存在急停判定变更；本日志没有足够的原始输入与接线语义，不能判断其极性是否正确。

## 7. 建议的整理方向（未实施）

### 7.1 故障分为立即抑制、异步处理和最终通知

用户要求“先处理错误再置故障”应落实为：一旦错误出现，立即禁止新测试和新运动，并记录首个错误；随后处理停止和收尾；最后进入面向用户的最终故障状态并通知。不能在等待清理时继续对外表现为可正常运行。

```text
首次错误
  → 故障处理中：锁住启动，保留原始原因，拒绝重复推进
  → 请求停止运动、结束采集、按状态结束实验表
  → 各项得到成功 / 失败 / 超时结果
  → 发布最终故障结果及一次汇总提示
```

后续错误追加为清理失败原因，不递归启动另一轮 `failExecution()`。停止、结表均有唯一请求入口和在途状态；已经提交的请求只等待结果。超时必须转为明确的失败结果，不能无限占用“收尾中”。

### 7.2 故障允许发起恢复，成功仍需要事实确认

“故障一定可以复位”应解释为故障中始终有可发起、可重试、可解释的恢复路径，而不是设备仍运动或安全条件不满足时强制宣告复位成功。

复位请求不应仅因为上一轮残留的软件状态被一概拒绝。恢复入口应接管故障清理，处理在途操作，必要时停止硬件，再验证新鲜状态。状态 0 但轴仍运动时也应有合适的硬件停止路径；不应只按实验程序是否活动决定能否停止。

恢复需关联执行/命令代次，隔离迟到回调；采集和数据库未完成的操作需等待明确结果或采用有定义的取消/失败处理，不能只清空标志。确认运动、安全条件及各服务状态后才回到可启动状态。失败或超时则保留故障，指出具体未恢复项并允许重试。

### 7.3 最小改动先统一语义，不增加更多散落布尔值

将已有状态按责任区分：硬件快照保存实际观测；命令状态表示移零/停止/复位是否在途；流程状态表示运行/故障处理/最终故障。硬件快照不由业务故障处理伪造覆盖。

优先把现有运动判断拆解为可记录的原因，让启动、停止、复位共享对这些原因的解释；不同动作仍可有不同准入条件。例如“不能启动”不应推导出“不能停止或恢复”。再收束命令完成、失败、断连和超时出口，避免先增加一批新标志。不要以无条件关闭 `hasActiveMotion()` 作为最终修复。

## 9. 后续验证范围

需覆盖：状态 0 且轴确实运动；状态 0 且仅速度超过阈值；移零提交失败、超时、断连；故障处理中重复报错/复位；数据库建表/结表回调延迟或丢失；旧回调晚到；Buffer 8 首帧、启动、结束和异常退出；恢复后重新启动。

验收重点是：拒绝理由可定位；故障处理有终点；每张表最多一次结束请求；停止路径覆盖实际运动；故障可以请求恢复；不能仅通过清空标志宣告恢复成功。硬件或模拟器上的验证需另行执行。本记录没有运行验证结果，也没有证明某个速度阈值或急停极性需要修改。
